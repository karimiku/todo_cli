設計書 v0.3 — Terminal-First Todo CLI

1. 目的 / 前提

ターミナルから即登録 → 順番厳守で片付けする超軽量 Todo。

v0 は個人利用のみ。配布・リリース・Docker はやらない。

SQLite を最初から使う。

バイナリ名は todo。エイリアスで tb/td も使う想定。

2. ユーザー体験（コマンド仕様）
   todo add <text> # 末尾に追加
   todo list # 未完了を上から順に番号表示（1 始まり）
   todo next # 一番上（=1）を完了（削除せず [x] 化）
   todo focus <id> # <id> を一番上へ（=最優先）
   todo move <id> <pos> # <id> を <pos> 番へ（1..N）
   todo delete <id> # 未完了から物理削除（誤登録用）
   todo edit <id> <text> # 未完了タスクの文言編集
   tb/td エイリアスも todo と同じヘルプ・メッセージを返す

ID の意味＝ list に表示される現在順位（1..N）。DB の内部 ID とは別。

list 出力例：

1 メール返信
2 図書館に本返却
3 買い出し

3. アーキテクチャ

言語: Go（cgo 不要ビルド）

DB: SQLite（WAL / busy_timeout / トランザクション）

保存パス: ~/.config/todo/todo.db（TODO_HOME があれば TODO_HOME/todo.db）

3.1 データモデル
Task {
id INTEGER // 内部 ID（PK, 自動採番）
text TEXT // 本文
is_done BOOL // 完了フラグ
order_key REAL // 並び順（小さいほど上）
created_at TEXT // ISO8601
updated_at TEXT
}

表示の ID は毎回、未完了に 1..N を再採番して見せる（内部 ID とは切り離し）。

order_key は 1.0 刻みを基本とし、move/focus では前後の値を参照して再計算する。ギャップが 1e-3 未満になった場合や極端な値になった場合は normalize で連番へ再採番する。

並び替えは order_key を直接更新（挿入時は末尾=最大+1.0、中間は平均値）。

3.2 スキーマ（初期化 SQL）
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 4000;

CREATE TABLE IF NOT EXISTS tasks (
id INTEGER PRIMARY KEY AUTOINCREMENT,
text TEXT NOT NULL,
is_done INTEGER NOT NULL DEFAULT 0,
order_key REAL NOT NULL,
created_at TEXT NOT NULL,
updated_at TEXT NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_tasks_undone_order
ON tasks(is_done, order_key);

4. ORM 選定（v0 の採用・理由・代替）
   4.1 採用：GORM + 純 Go SQLite ドライバ

理由

学習資料・例が豊富で最短で形にできる。

モデル定義/CRUD/マイグレーション/フック等が一通り揃う。

cgo 不要の純 Go ドライバ（例：github.com/glebarez/sqlite）と組み合わせ可。

接続方針

起動時に DB を開き、PRAGMA を Exec で適用（WAL・busy_timeout）。

オートマイグレーションで tasks を作成（v0 では十分）。

実装イメージ（※実装は不要、考え方のみ）

gorm.Open(sqlite.Open(dbPath), &gorm.Config{})

db.AutoMigrate(&Task{})

重要操作はトランザクションでラップ（db.Transaction(func(tx *gorm.DB) error { ... })）

4.2 代替（必要になったら）

Bun（SQL-first で薄い抽象）：生 SQL 寄りにしたくなったら検討。

sqlc（ORM ではないが、SQL→ 型安全コード生成）：生 SQL 派・最小依存で行く場合に。

v0 は GORM でスピード重視、将来 Bun/sqlc へ置き換えてもコマンド仕様は変えない方針。

5. コマンド別の動作仕様（DB 操作の要点）
   5.1 add <text>（末尾）

order_key = (未完了の MAX) + 1.0

is_done = 0, created_at/updated_at = NOW

クエリ要点：

SELECT COALESCE(MAX(order_key), 0) FROM tasks WHERE is_done=0;
INSERT INTO tasks(text,is_done,order_key,created_at,updated_at)
VALUES (?,0, max+1.0, NOW, NOW);

5.2 list（未完の 1..N + 完了）

未完了を ORDER BY order_key, id で取得 → 上から順に表示番号を付与

完了済みは番号なし [x] で必要分だけ表示（例: 直近 50）

5.3 next（先頭を完了／削除しない）

未完了の最小 order_key の 1 件を is_done=1 に更新

要点：

SELECT id FROM tasks WHERE is_done=0 ORDER BY order_key, id LIMIT 1;
UPDATE tasks SET is_done=1, updated_at=NOW WHERE id=?;

5.4 focus <id>（表示順位 → 一番上へ）

トランザクション内で実行。
- rows := SELECT id, order_key, text FROM tasks WHERE is_done=0 ORDER BY order_key, id;
- rows が空なら「未完了はありません 🎉」。
- 指定 ID が範囲外なら tx.Rollback() して「未完了の件数は N 件です」。
- displayID=1 の場合は order_key を変更せず updated_at とメッセージのみ更新。
- それ以外は minOrder := rows[0].order_key、newOrder := minOrder - focusStep (focusStep=1.0)。
- UPDATE tasks SET order_key=newOrder, updated_at=NOW WHERE id=targetID。
- newOrder が -1e9 未満、または minOrder-newOrder < 1e-6 なら normalize を後段で実施。

成功時は「⇡ 最優先に移動: <text>」。

5.5 move <id> <pos>（任意位置へ）

トランザクション内で display ID と目標順位を解決。
- rows := SELECT id, order_key, text FROM tasks WHERE is_done=0 ORDER BY order_key, id;
- rows が空なら「未完了はありません 🎉」。ID が範囲外なら「未完了の件数は N 件です」。
- pos < 1 はエラー「順位は 1 以上を指定してください」。pos > len(rows) は len(rows) に丸める。
- target := rows[idx]。新しい挿入位置から prev/next の order_key を取得。
- pos-1 == idx の場合は移動無し。pos-1 != idx のとき:
  - 先頭移動: newOrder := rows[0].order_key - 1.0
  - 末尾移動: newOrder := rows[last].order_key + 1.0
  - 中間: newOrder := (prev.order_key + next.order_key) / 2
- UPDATE tasks SET order_key=newOrder, updated_at=NOW WHERE id=target.id。
- math.Abs(prev.order_key-next.order_key) < 1e-3 の場合は normalize を実行。

成功時は「⇄ 順番変更: <text> → <pos>」。

5.5.1 order_key normalize

normalize は move/focus 後にキューイングし、同一トランザクション内または直後に実施する。
- SELECT id FROM tasks WHERE is_done=0 ORDER BY order_key, id;
- 1.0 刻みで order_key を 1.0, 2.0, ... に再採番し、bulk UPDATE。
- 操作中に追加/削除があっても矛盾が出ないよう、同一 tx でまとめて更新する。

5.6 delete <id>（物理削除）

表示 ID→ 内部 ID を解決後、DELETE。
- rows := SELECT id, text FROM tasks WHERE is_done=0 ORDER BY order_key, id;
- 範囲外なら「未完了の件数は N 件です」。rows が空なら「未完了はありません 🎉」。
- tx.Exec("DELETE FROM tasks WHERE id=? AND is_done=0", targetID)。
- RowsAffected==0 の場合はエラー扱い（理論上発生しないが二重防御）。

成功時は「🗑 削除: <text>」。

5.7 edit <id> <text>

表示 ID→ 内部 ID を解決。
- 入力テキストは strings.TrimSpace で前後を除去し、len==0 なら「空のテキストは不可」。
- UPDATE tasks SET text=?, updated_at=NOW WHERE id=? AND is_done=0。
- RowsAffected==0 の場合は範囲外 ID と同等のエラー。

成功時は「✎ 更新: <text>」。

5.8 CLI エイリアス・ヘルプ

os.Args[0] が todo/tb/td のいずれでも同じコマンドセットを提供。
- usage/ヘルプ文には「todo (tb/td)」と併記。
- `todo --help` やエラー時の usage でも alias 名を表示し、ユーザがエイリアス経由でも迷わないようにする。

いずれも 1 操作=1 トランザクションで整合性担保。
busy_timeout 設定でロック競合は自動リトライ（並列実行は基本想定しない）。

6. エラーポリシー / メッセージ

範囲外 ID: 「未完了は N 件です」

add/edit の空文字: 「空のテキストは不可」

move の pos<1: 「順位は 1 以上を指定してください」

next で未完 0: 「未完了はありません 🎉」

成功メッセージは動詞 + 対象タスクを含め、CLI から視認しやすくする。

失敗時は短文で理由を即出し（使い方/usage も短い行で表示）

7. 非機能

体感レスポンス < 300ms（ローカル）

依存: Go 標準 + GORM + 純 Go SQLite ドライバ

ログ・テレメトリ: なし（env でデバッグログは任意 ON）

9.1 ブランチ構成（3 インスタンス並列開発対応）

main

- メインブランチ。すべての成果物を統合する
- 各機能ブランチからの PR を受け取り Squash Merge

infra/foundation

- **担当**: インスタンス 1
- **役割**: プロジェクト基盤の構築
- **作業内容**:
  - README/LICENSE/.gitignore/go.mod の作成
  - SQLite 接続・GORM 初期化・PRAGMA 設定
  - Task 構造体の定義
  - TODO_HOME などの設定パス解決ロジック
  - 引数パース・サブコマンドディスパッチの基盤
- **最終目標**: 他のブランチが依存できる基盤を構築

feature/core-commands

- **担当**: インスタンス 2
- **役割**: 基本 3 コマンド（add/list/next）の実装
- **依存**: infra/foundation の内容が必要
- **作業内容**:
  - add コマンド: タスク追加・order_key 計算
  - list コマンド: 未完了リスト表示（1..N）、完了タスク表示
  - next コマンド: 先頭完了処理
  - 基本エラーハンドリング
  - 最小限の統合テスト
- **最終目標**: 基本的な todo 操作が動作する状態

feature/extended-commands

- **担当**: インスタンス 3
- **役割**: 拡張コマンド（focus/move/edit/delete）の実装
- **依存**: infra/foundation + feature/core-commands の内容が必要
- **作業内容**:
  - focus コマンド: ID 解決・最上位移動ロジック
  - move コマンド: 任意位置への再配置・範囲外処理
  - edit コマンド: テキスト編集・空文字チェック
  - delete コマンド: 物理削除
  - tb/td エイリアス対応
  - UX 改善（ヘルプ表示・メッセージ整形）
- **最終目標**: 全コマンドが動作し、エイリアスも使える完成状態

進行フロー:

1. infra/foundation → main (基盤完成)
2. feature/core-commands → main (基本動作)
3. feature/extended-commands → main (完全版完成)
