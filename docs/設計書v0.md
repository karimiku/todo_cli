# 設計書 v0.3 — Terminal-First Todo CLI

## 1. 目的 / 前提
- ターミナルから即登録 → 順番厳守で片付ける超軽量 Todo。
- v0 は個人利用のみ（配布・リリース・Docker は対象外）。
- 依存 DB として SQLite を前提採用。
- バイナリ名は `todo`。エイリアス `tb` / `td` も同じ挙動を提供する。

## 2. ユーザー体験（コマンド仕様）
| コマンド | 説明 |
| --- | --- |
| `todo add <text>` | 未完了タスクを末尾に追加する |
| `todo list` | 未完了を 1 始まりで番号表示し、完了済みを別枠 `[✅]` で表示 |
| `todo next` | 先頭タスクを完了（[✅] 化）するが削除はしない |
| `todo focus <id>` | 指定 ID を最上位へ移動する |
| `todo move <id> <pos>` | 指定タスクを `<pos>` 番へ移動（1..N） |
| `todo delete <id>` | 未完了タスクを物理削除する |
| `todo edit <id> <text>` | 未完了タスクの本文を更新する |
| `tb` / `td` | `todo` と同一のヘルプ・メッセージ・挙動 |

- 表示上の ID は現在の未完了リストの順位（1..N）であり、DB の内部 ID とは別物。

### list 出力例
```
1 メール返信
2 図書館に本返却
3 買い出し

---

[✅] 会議メモ整理
```

## 3. アーキテクチャ概要
- 言語: Go（cgo 不要ビルド）。
- DB: SQLite（WAL / busy_timeout / トランザクション）。
- 保存パス: `~/.config/todo/todo.db`（`TODO_HOME` があれば `TODO_HOME/todo.db`）。

### 3.1 データモデル
```
Task {
  id         INTEGER  // PK, AUTOINCREMENT
  text       TEXT     // 本文
  is_done    BOOL     // 完了フラグ
  order_key  REAL     // 並び順（小さいほど上）
  created_at TEXT     // ISO8601
  updated_at TEXT
}
```
- 未完了タスクは毎回 1..N で再採番して表示する。
- `order_key` は 1.0 刻みを基本とし、`move`/`focus` で前後値を参照して再計算。
- ギャップが 1e-3 未満、または極端値に接近した場合は normalize で連番に再採番。

### 3.2 スキーマ（初期化 SQL）
```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 4000;

CREATE TABLE IF NOT EXISTS tasks (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  text TEXT NOT NULL,
  is_done INTEGER NOT NULL DEFAULT 0,
  order_key REAL NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_tasks_undone_order
  ON tasks(is_done, order_key);
```

## 4. ORM / インフラ選定
### 4.1 採用: GORM + 純 Go SQLite ドライバ
- 学習資料が豊富で短期間で実装できる。
- モデル定義、CRUD、マイグレーション、フックなど必要機能が揃っている。
- `github.com/glebarez/sqlite` と組み合わせることで cgo 不要。
- 起動時に DB を開き、PRAGMA を `Exec` で適用。`AutoMigrate` で `tasks` テーブルを作成。
- 重要操作は `db.Transaction(...)` でトランザクション化する。

### 4.2 代替候補
- Bun（SQL-first、薄い抽象）。
- sqlc（SQL → 型安全コード生成）。
- v0 は GORM でスピード重視。将来置き換えても CLI 仕様は維持する。

## 5. コマンド別動作仕様（DB 観点）
### 5.1 `add <text>`
- `order_key = COALESCE(MAX(order_key), 0) + 1.0`。
- `is_done = false`、`created_at`/`updated_at = NOW`。
- INSERT 後に追加タスクを返す。

### 5.2 `list`
- `ORDER BY order_key ASC, id ASC` で未完了を取得し、1..N を付与。
- 完了済みは `ORDER BY updated_at DESC, id DESC LIMIT 50` で取得し、`[✅]` で表示。

### 5.3 `next`
- 未完了の最小 `order_key` タスクを 1 件取得し、`is_done=true` に更新。
- 未完了ゼロの場合は「未完了はありません 🎉」。

### 5.4 `focus <id>`
- トランザクション内で未完了タスクの `id`, `order_key`, `text` をロックして取得。
- rows が空: 「未完了はありません 🎉」。
- 範囲外 ID: 「未完了の件数は N 件です」。
- displayID=1: `order_key` は変えず `updated_at` のみ更新。
- それ以外: `newOrder = minOrder - focusStep (1.0)`。
- `newOrder < -1e9` もしくは `minOrder - newOrder < 1e-6` の場合は normalize を実施。
- 成功メッセージ: `⇡ 最優先に移動: <text>`。

### 5.5 `move <id> <pos>`
- トランザクション内で未完了タスク一覧をロック取得。
- rows が空: 「未完了はありません 🎉」。範囲外 ID: 「未完了の件数は N 件です」。
- `<pos> < 1`: エラー「順位は 1 以上を指定してください」。`<pos> > len`: len に丸める。
- 同じ順位: `updated_at` を更新し、`⇄ 順番変更: <text> → <pos>` を表示。
- 先頭／末尾／中間で `newOrder` をそれぞれ計算。
- 前後の `order_key` 差が 1e-3 未満なら normalize を実行。

### 5.5.1 order_key normalize
- `SELECT id FROM tasks WHERE is_done=0 ORDER BY order_key, id`。
- 1.0, 2.0, … と再採番し、同一トランザクション内でまとめて `UPDATE`。

### 5.6 `delete <id>`
- 未完了タスクをロックして解決後、`DELETE`。
- RowsAffected==0 の場合はエラー。
- 成功メッセージ: `🗑 削除: <text>`。

### 5.7 `edit <id> <text>`
- 未完了タスクをロックして解決後、`text` と `updated_at` を更新。
- `TrimSpace` 後の文字列が空なら「空のテキストは不可」。
- 成功メッセージ: `✎ 更新: <text>`。

### 5.8 CLI エイリアス・ヘルプ
- `os.Args[0]` が `todo` / `tb` / `td` のいずれでも同じコマンドセットを提供。
- `usage` にはエイリアス名も併記し、`todo --help` / エラー時も同様に表示。
- 1 操作 = 1 トランザクションで整合性を担保。`busy_timeout` でロック競合は自動リトライ。

## 6. エラーポリシー / メッセージ
| 事象 | メッセージ |
| --- | --- |
| 範囲外 ID | 「未完了は N 件です」 |
| `add` / `edit` の空文字 | 「空のテキストは不可」 |
| `move` の `<pos> < 1` | 「順位は 1 以上を指定してください」 |
| 未完了ゼロで `next` | 「未完了はありません 🎉」 |

- 成功メッセージは操作の動詞 + 対象タスクを含める。
- 失敗時は理由を短文で返し、`usage` も同時に提示する。

## 7. 非機能要件
- 体感レスポンス < 300ms（ローカル）。
- 依存: Go 標準 + GORM + 純 Go SQLite ドライバ。
- 耐久性: WAL / トランザクション / NORMAL 同期設定。
- ログ＆テレメトリなし（必要に応じて環境変数でデバッグログ）。

## 8. Git / GitHub 運用方針
- ブランチ命名: `feat/<topic>`、`fix/<topic>`、`docs/<topic>`。
- `main` 直コミット禁止。PR を作成しセルフレビュー後に Squash Merge。
- コミット規約: Conventional Commits（例: `feat: implement next command`）。
- v0 はタグ／リリース不要（学習目的で付けたい場合は任意）。

## 9. ローカル開発フロー（v0）
1. リポジトリ作成 → `README` / `LICENSE` / `.gitignore` / `go.mod` を用意。
2. `feat/sqlite-store`: スキーマ初期化・接続層（GORM, PRAGMA 適用）。
3. `feat/commands-core`: `add` / `list` / `next` を実装。
4. `feat/reorder`: `focus` / `move` を実装。
5. `feat/fixes`: `delete` / `edit` と境界エラー整備。
6. 動作確認後にドキュメント更新（使い方・保存先・エイリアス例）。

### 9.1 ブランチ構成（3 インスタンス並列開発想定）
- **main**: すべての成果物を統合。各機能ブランチからの PR を受け取り Squash Merge。
- **infra/foundation**（担当: インスタンス 1）
  - README/LICENSE/.gitignore/go.mod 作成
  - SQLite 接続・GORM 初期化・PRAGMA 設定
  - Task 構造体定義、`TODO_HOME` 等のパス解決
  - 引数パース・サブコマンドディスパッチ基盤
- **feature/core-commands**（担当: インスタンス 2）
  - `add` / `list` / `next` 実装
  - 基本エラーハンドリングと最小統合テスト
- **feature/extended-commands**（担当: インスタンス 3）
  - `focus` / `move` / `edit` / `delete` 実装
  - `tb` / `td` エイリアス対応
  - ヘルプ表示・メッセージ整形など UX 改善

進行フロー: `infra/foundation` → `feature/core-commands` → `feature/extended-commands` の順で main へ統合。

## 10. 将来拡張メモ（v0 外）
- `order_key` のバッチ normalize（大量操作時の保守）。
- `purge`（完了タスク一括削除）、`undo`（直前操作戻し）。
- SwiftBar 連携 `todo bar`（右上ワンクリック運用）。
- FTS5 検索、エクスポート（JSON/NDJSON）、バックアップ機能。
